# Async Handler

A queue-agnostic asynchronous task processing system. It consumes messages from a queue, dispatches them to registered process handlers, and manages retries and dead-letter routing at the application level.

## Architecture

```
                                ┌─────────────────────────────────┐
                                │          HTTP Service           │
                                │  (or any internal service)      │
                                └──────────────┬──────────────────┘
                                               │
                                      Dispatcher.Dispatch()
                                               │
                                               ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│                            Queue (interface)                                 │
│                                                                              │
│   Enqueue()  ◄─── Dispatcher / Retry        Consume() ───►  AsyncHandler    │
│   Acknowledge()  ◄─── on success            SendToDLQ() ◄── on max retries  │
│                                                                              │
│   Implementations: SQS (prod) │ Dummy (dev)                                 │
└──────────────────────────────────────────────────────────────────────────────┘
                                               │
                                          callback per
                                           message
                                               │
                                               ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│                           AsyncHandler.Start()                               │
│                                                                              │
│   ┌─────────────┐     semaphore (buffered chan, size = WorkerCount)          │
│   │  Consume     │───► acquire slot ───► go processMessage()                 │
│   │  callback    │                          │                                │
│   └─────────────┘                          ▼                                │
│                              ┌──────────────────────────┐                    │
│                              │   Deserialize envelope    │                    │
│                              │   Lookup ProcessType in   │                    │
│                              │   registry map            │                    │
│                              │   Execute handler         │                    │
│                              │   Ack / Retry / DLQ       │                    │
│                              └──────────────────────────┘                    │
└──────────────────────────────────────────────────────────────────────────────┘
```

## Message Envelope

Every message on the queue follows this JSON schema:

```json
{
  "messageId":   "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "processType": "SITE_INTELLIGENCE_PROCESS",
  "userId":      "mongo-object-id",
  "payload":     { "webEntityId": "xyz789" },
  "metadata": {
    "retryCount":    0,
    "maxRetries":    3,
    "source":        "dispatcher",
    "correlationId": "req-uuid",
    "createdAt":     "2026-04-02T10:00:00Z"
  }
}
```

| Field | Type | Purpose |
|-------|------|---------|
| `messageId` | UUID string | Idempotency key. Generated by the dispatcher. |
| `processType` | string enum | Routes to the correct `ProcessHandler` via the registry. |
| `userId` | string | Every operation is user-scoped. Always present. |
| `payload` | `json.RawMessage` | Process-specific data. Each handler deserializes into its own typed struct. |
| `metadata.retryCount` | int | Incremented by the worker on each failure. Starts at 0. |
| `metadata.maxRetries` | int | When `retryCount >= maxRetries`, the message goes to DLQ. |
| `metadata.source` | string | Which system published the message (for multi-producer tracing). |
| `metadata.correlationId` | UUID string | Ties back to originating request or parent process. |
| `metadata.createdAt` | RFC 3339 | Timestamp of initial dispatch. |

## Queue Interface

Defined in `internal/providers/interfaces/queue.go`:

```go
type MessageCallback func(ctx context.Context, body []byte, receiptHandle string)

type Queue interface {
    Consume(ctx context.Context, callback MessageCallback) error
    Enqueue(ctx context.Context, body []byte) error
    Acknowledge(ctx context.Context, receiptHandle string) error
    SendToDLQ(ctx context.Context, body []byte) error
}
```

- **`Consume`** — blocks, long-polls the queue, and invokes `callback` once per message. Stops when `ctx` is cancelled.
- **`Enqueue`** — publishes a raw JSON body to the primary queue. Used by the dispatcher for new messages and by the worker for retries.
- **`Acknowledge`** — removes a message from the queue (SQS: `DeleteMessage`). Called after successful processing or before re-enqueue/DLQ.
- **`SendToDLQ`** — publishes a raw JSON body to the dead-letter queue.

The interface operates on `[]byte` (raw JSON) and opaque `receiptHandle` strings. This keeps it backend-agnostic — any queue system that can send/receive bytes and track message receipts can implement it.

### Swapping queue backends

To add a new backend (e.g., RabbitMQ, Redis Streams):

1. Create `internal/providers/impl/<backend>/<backend>.go` implementing `interfaces.Queue`.
2. Create a corresponding `dummy.go` for development.
3. Add an inject function in `cmd/service/providers/` (following `sqs.go` pattern).
4. Call the inject function from `InjectDefaultProviders` in `providers.go`.

No changes to the async handler, dispatcher, or any business service.

## Concurrency Model

The async handler uses a **semaphore pattern** for bounded concurrency:

```
Consume callback
    │
    ▼
sem <- struct{}{}    ← blocks if WorkerCount goroutines are already running
wg.Add(1)
    │
    ▼
go func() {
    defer wg.Done()
    defer { <-sem }  ← release slot
    processMessage()
}
```

- **`sem`** is a buffered channel of size `WorkerCount`. Each message acquisition blocks on the semaphore, so at most `WorkerCount` goroutines run concurrently.
- **`wg`** (`sync.WaitGroup`) tracks all in-flight goroutines for graceful shutdown.
- Each goroutine is **self-contained** — it deserializes, dispatches, handles retry/DLQ, and acknowledges independently.

## Message Processing Flow

```
1. Deserialize body → MessageEnvelope
   ├─ failure → SendToDLQ(raw body) + Acknowledge → done
   │
2. Lookup msg.ProcessType in registry
   ├─ not found → SendToDLQ(raw body) + Acknowledge → done
   │
3. Execute handler(ctx, msg)
   ├─ success → Acknowledge → done
   │
   └─ failure → handleFailure:
        ├─ Acknowledge original message (prevent SQS redelivery)
        ├─ Increment retryCount
        ├─ retryCount >= maxRetries → SendToDLQ(updated envelope)
        └─ retryCount < maxRetries  → Enqueue(updated envelope)
```

Key detail: the original message is **always acknowledged** before re-enqueue or DLQ. This prevents SQS's native visibility timeout from causing duplicate processing. Retry is application-controlled.

## Process Registry

The registry maps `ProcessType` → `ProcessHandler`:

```go
type ProcessHandler func(ctx context.Context, msg MessageEnvelope) error
```

Currently registered processes:

| ProcessType | Constant | Handler | Service Method |
|-------------|----------|---------|----------------|
| `SITE_INTELLIGENCE_PROCESS` | `ProcessSiteIntelligence` | `buildSiteIntelligenceHandler` | `SiteIntelligenceService.Process()` |
| `PROCESS_ONBOARDED_USER` | `ProcessOnboardedUser` | `buildOnboardedUserHandler` | `OnboardingService.ProcessOnboardedUser()` |
| `GET_COMPETITOR_INFO` | `ProcessGetCompetitors` | `buildGetCompetitorsHandler` | `OnboardingService.GetCompetitorInfo()` |

### Adding a new process

1. **Define the process type constant** in `registry.go`:
   ```go
   const ProcessMyNewTask ProcessType = "MY_NEW_TASK"
   ```

2. **Define the payload struct** in `registry.go`:
   ```go
   type MyNewTaskPayload struct {
       SomeField string `json:"someField"`
   }
   ```

3. **Write the handler builder** in `registry.go`:
   ```go
   func buildMyNewTaskHandler(locator *ServiceLocator) ProcessHandler {
       return func(ctx context.Context, msg MessageEnvelope) error {
           var p MyNewTaskPayload
           if err := json.Unmarshal(msg.Payload, &p); err != nil {
               return fmt.Errorf("unmarshal my new task payload: %w", err)
           }
           return locator.SomeService.DoWork(ctx, msg.UserID, p.SomeField)
       }
   }
   ```

4. **Register it** in `BuildProcessRegistry`:
   ```go
   ProcessMyNewTask: buildMyNewTaskHandler(locator),
   ```

5. **If the handler needs a new service**, add it to `ServiceLocator`:
   ```go
   type ServiceLocator struct {
       // ... existing fields
       SomeService somepackage.SomeService
   }
   ```
   And wire it in `BuildAsyncHandler` in `providers.go`.

## Dispatcher

The `Dispatcher` interface lives in `internal/providers/interfaces/dispatcher.go`:

```go
type Dispatcher interface {
    Dispatch(ctx context.Context, processType string, userID string, payload any) error
}
```

The implementation in `asyncHandler/dispatcher.go`:
- Accepts a typed `payload any` and calls `json.Marshal` internally.
- Builds the full `MessageEnvelope` with a generated `messageId`, `correlationId`, and timestamps.
- Serializes the envelope and calls `Queue.Enqueue`.

### Using the dispatcher from a service

Services receive `interfaces.Dispatcher` via their constructor (injected at DI time in `providers.go`). To dispatch:

```go
err := d.Dispatch(ctx, string(asyncHandler.ProcessSiteIntelligence), userId,
    asyncHandler.SiteIntelligencePayload{WebEntityID: webEntityId},
)
```

### Process chaining

A process handler can itself dispatch follow-up work. Since `ServiceLocator` provides access to business services, and those services hold a `Dispatcher`, chains happen naturally:

```
HTTP Request
  └─► OnboardingService.OnboardUser()
        └─► dispatcher.Dispatch(PROCESS_ONBOARDED_USER, ...)
              └─► [queue] ─► AsyncHandler
                    └─► OnboardingService.ProcessOnboardedUser()
                          └─► dispatcher.Dispatch(SITE_INTELLIGENCE_PROCESS, ...)
                                └─► [queue] ─► AsyncHandler
                                      └─► SiteIntelligenceService.Process()
```

## Dependency Injection Order

Wired in `cmd/service/providers/providers.go` and `cmd/service/app-service.go`:

```
1. LoadConfigFromEnv        → SQSConfig, AsyncHandlerConfig loaded
2. InjectDefaultProviders   → Queue (SQS or Dummy)
                            → Dispatcher (depends on Queue)
3. InjectDefaultServices    → Business services (can receive Dispatcher)
4. BuildAsyncHandler        → ServiceLocator (from services)
                            → ProcessRegistry (from ServiceLocator)
                            → AsyncHandler (from Queue + Registry + config)
5. asyncHandler.Start(ctx)  → runs in goroutine alongside HTTP server
```

No circular dependencies. The `asyncHandler` package imports service interfaces (one-way). The `config` package imports `providers/interfaces` (one-way). The `Dispatcher` interface lives in `providers/interfaces` to break any potential cycle.

## Lifecycle and Graceful Shutdown

The async handler runs in-process alongside the HTTP server, controlled by a shared `context.Context`:

```go
ctx, cancel := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)

go asyncHandler.Start(ctx)   // background
srv.ListenAndServe()          // foreground
```

On shutdown (SIGINT/SIGTERM):

1. Context is cancelled.
2. `Queue.Consume` stops fetching new messages.
3. Semaphore gate blocks (no new goroutines dispatched).
4. `sync.WaitGroup.Wait()` blocks until all in-flight goroutines complete.
5. If `ShutdownTimeout` is exceeded, the handler logs a warning and exits. Unfinished messages reappear in SQS after visibility timeout.

In-flight processes are allowed to **run to completion** — no early cancellation. This avoids partially-completed work that's harder to reason about than a full retry.

### Extracting to a separate binary

To scale workers independently from the API server:

1. Create `cmd/worker/main.go`.
2. Call `ProvideAppContext(appCtx)` (already reusable).
3. Call `providers.BuildAsyncHandler(appCtx)`.
4. Call `asyncHandler.Start(ctx)` as the main blocking call.

No changes to the `asyncHandler` package or any business service.

## Configuration

### Environment Variables

| Variable | Default | Description |
|----------|---------|-------------|
| `SQS_QUEUE_URL` | — | Primary SQS queue URL |
| `SQS_DLQ_URL` | — | Dead-letter queue URL |
| `SQS_WAIT_TIME_SECONDS` | `20` | Long-poll duration (max 20 for SQS) |
| `SQS_VISIBILITY_TIMEOUT` | `300` | Seconds a message is hidden after receipt. Must exceed your longest process time. |
| `ASYNC_WORKER_COUNT` | `5` | Max concurrent goroutines processing messages |
| `ASYNC_MAX_RETRIES` | `3` | Retry attempts before routing to DLQ |
| `ASYNC_SHUTDOWN_TIMEOUT_SECONDS` | `30` | Max wait time for in-flight processes during shutdown |

| Variable | Default | Description |

| `AWS_ACCESS_KEY_ID` | — | IAM access key |
| `AWS_SECRET_ACCESS_KEY` | — | IAM secret key |

### Development Mode

When `ENVIRONMENT != "production"`, the dummy SQS provider is injected. It:
- Blocks on `Consume` until context cancellation (no polling).
- Logs `Enqueue` calls (no-op).
- No-ops on `Acknowledge` and `SendToDLQ`.

This means the async handler starts silently in dev and does nothing unless you explicitly set SQS env vars and switch to production mode.

## Logging

All log points use the project's `internal/util/log` package (structured JSON via `slog`):

| Event | Level | Fields |
|-------|-------|--------|
| Message received | INFO | processType, messageId, userId, retryCount |
| Process succeeded | INFO | processType, messageId, duration |
| Process failed (retrying) | ERROR | error, processType, messageId, userId, retryCount, duration |
| Max retries exceeded → DLQ | WARN | processType, messageId, retryCount, correlationId |
| Unknown processType → DLQ | ERROR | processType, messageId |
| Deserialization failure → DLQ | ERROR | error |
| Consumer starting/stopping | INFO | workerCount |
| Shutdown timeout exceeded | WARN | — |

Every log line includes `messageId` for tracing individual messages through the system. Use `correlationId` to trace back to the originating HTTP request or parent process in a chain.
